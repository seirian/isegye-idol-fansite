# 모니터링 갱신 장애와 배치 반영 결과 분리

2026-11-17 사용자가 원인 검토 후 수정 구현과 운영 배포를 승인했다.

## 화면과 보관

모니터링 갱신 지연/조회 실패, 새 회차 확인 대기, 실제 반영 결과를 구분한다.
마지막 정상 확인은 확인 시각·대상 회차·검증 근거 실행과 함께 별도로 보존한다.
과거 성공을 현재 성공으로 바꾸지 않으며 지연 상태에서 현재 정상 집계는 0이다.
전체가 확인 불가라는 문구로 과거 검증을 지우지 않는다. 게시 근거 미확인과
실제 배치의 반영 확인 필요도 구분한다. 복구 점검에는 게시 완료라는 표현을 쓰지 않는다.

서버의 해시 검증된 이전 스냅샷에서 최소 필드만 이관한다. 새 스냅샷의 오류/상태는
덮어쓰지 않는다. 실패한 점검은 이미 확인한 동일 회차의 이력도 삭제하지 않는다.
90일 이력 및 활성/복구본 포함 24개 물리 스냅샷 경계는 유지한다.

## 수집기 상태

collectorHealth는 배치 결과와 독립된 ok/degraded/failed다. 실패한 배치를 정확히
읽은 것은 정상 점검이다. 조회 자체 실패, 불완전 이력, 게시 근거 미확인은 따로 센다.
모든 조회 실패 시에도 진단 파일을 만들어 보호된 모니터링에 게시할 수 있지만,
수집 프로세스와 정기 갱신 워크플로가 성공으로 끝나지 않는다. 부분 점검 미완료도
갱신 워크플로를 실패로 표시한다. 공개 산출물에는 합계/오류 분류만 기록하고
실제 data.json, 계정·인증정보·원본 오류 내용은 포함하지 않는다.

## 자동 갱신과 복구

10분 예약은 유지한다. 6개 수집 배치, 운영 배포 및 기존 복구 점검 종료를 추가
기동 경로로 사용한다. 성공뿐 아니라 실패·취소도 포함한다. 같은 저장소 main의
허용된 워크플로인지 원본 API로 재확인한다. PR/포크 이벤트, 자기 자신, 새 복구
워크플로는 기동 대상이 아니다. 실행 중 갱신을 취소하지 않고 대기 요청만 합친다.
기존 공통 production 큐/서버 쓰기 잠금/중지 변수는 유지한다.

별도 batch-monitoring-health.yml은 매시 04/24/44분에 모니터링 상태를 점검한다.
오래된 실행의 재시도를 포함한 활성 실행이 있으면 중복 실행하지 않는다. 최근 2시간
생성 이력을 완전 조회하고 15분 재요청 대기 및 시간당 신규 수동·복구 요청 2개
상한을 적용한다. 30분 이내의 해시/출처 검증된 게시 보고서와 점검 품질이 없으면
monitoring 워크플로만 요청한다. 기존 수집 배치는 실행하지 않으며 SFTP 비밀값은
이 복구기에 전달하지 않는다. 요청 직전 재확인, 조회/무결성 오류 시 요청 금지.
복구 요청/예산 소진/점검 실패는 성공으로 숨기지 않고 Actions 실패로 남긴다.

두 예약은 모두 GitHub에 의존하므로 GitHub 전체 예약 장애에 독립적인 시스템이라고
주장하지 않는다. 서버 cron 지원 및 독립 실행 자격은 확인되지 않았으며 새 서버
권한/시크릿/외부 유료 서비스는 추가하지 않는다. 기존 복구 점검 완료 이벤트가
예약 외 경로이며, 독립 스케줄러는 별도 인프라 확인 후 추가할 수 있다.

## 완료 기준

기존 관리자 권한·안내 이동·라이트/다크 UI를 유지한다. 전체 API 실패, 부분 실패,
동일 회차 이력 보존, 새 회차 경계, 45분 이상 지연, PC/모바일, 권한 상실을 검사한다.
코드 검증과 실제 게시를 구분하고 게시 파일 해시 및 접근 제한을 재조회한다.
운영 후 최소 2회 상태 갱신의 게시 보고서를 대조한다. 예약 실행 검증과 수동/이벤트
실행 검증은 구분해서 기록하며 아직 발생하지 않은 예약 성공을 주장하지 않는다.
