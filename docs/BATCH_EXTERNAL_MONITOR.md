# 독립 정기 점검과 제한된 watchdog 기동

## 목적과 경계

실제 수집·게시·현재 main 배포의 최신 검증을 확인한다. GitHub 내부 예약의 지연을
관찰하는 외부 점검은 기존 시간별 일정을 유지한다. 신규 cron·토큰·서버 권한을
추가하지 않는다. 개별 배치를 외부에서 직접 실행하지 않는다.

외부 연결의 GitHub.fetch는 저장소 실행 목록을 읽을 수 있지만 워크플로 정의 경로의
목록은 지원하지 않는다(2026-11-24 실제 400 INVALID_ARGUMENT). 이는 계정 권한
부족이 아니다. URI 변형·새 토큰·접근 우회로 해결하지 않는다. 실제 실행을 허용할
완전 조회는 고정 코드 `batch_watchdog_wakeup.py`가 GitHub 내부에서 수행한다.

## 조회와 기동 순서

1. 현재 KST, main SHA, 이 문서·BATCH_RELIABILITY.md와 두 watchdog workflow의
   현재 정책을 확인한다. 정책·중지 명령은 항상 최신 지시가 우선이다.
2. 저장소 실행 목록 첫 페이지에서 `batch-watchdog-wakeup.yml`의 같은 저장소 main
   실행을 찾는다. 이는 작업 식별용이며 전역 최신 attempt·활성 부재 증명이 아니다.
   저장된 검증 실행 ID가 있으면 해당 run을 직접 읽을 수 있다. 오래된 전체 저장소
   이력을 끝까지 읽는 작업을 기본 경로로 사용하지 않는다.
3. 대상 run의 저장소·head_repository·main·경로·head SHA를 확인한다. 재실행 대상
   workflow 정의가 현재 main의 검토된 정의와 같은지 대조한다. 생성 후 30일에
   가까운 run을 계속 재사용하지 않고 기존 콘텐츠 완료로 생긴 최근 audit seed를
   사용한다. 적합한 seed가 없으면 미완료로 남긴다.
4. 조회한 기동 작업이 active면 요청하지 않는다. 최신 attempt가 15분 이내이면
   추가 요청하지 않는다. 이미 해당 회차의 검증이 충분하면 불필요한 기동을 하지
   않는다. 오래된 보고서의 active/cooldown은 현재 상태로 해석하지 않는다.
5. 필요할 때 검증된 기동 작업의 최신 attempt job ID만 `rerun_workflow_job`로 최대
   한 번 요청한다. 이 작업은 단일 job이며 Production/수집 후속 job이 없다.
   target watchdog의 활성·과거 완료 attempt·쿨다운·상한을 확정하는 최종 책임은
   기동 작업 내부의 새 전체 조회에 있다. 외부에서 부재를 추정해 개별 배치를
   실행할 수 있는 권한으로 확장하지 않는다.
6. 최신 attempt의 `batch-watchdog-wakeup-<runId>-<attempt>` 산출물 또는 판단 로그를
   확인한다. 가능한 경우 원본 ZIP의 크기·SHA-256과 provenance를 직접 검증한다.
   산출물 목록/로그만 확인한 경우 원본 해시 검증과 구분한다.
7. `dispatched`는 기존 watchdog 요청 수락이며 게시 완료가 아니다. 후속 watchdog
   보고서와 필요한 게시/배포 산출물의 실제 source/generated/published/readback 및
   main SHA를 대조한다. 진행 중이면 다음 기존 점검에서 확인한다.

## 호출 예산과 미확인 요청

한 점검의 GitHub 호출은 재시도·재실행·상태 조회를 포함하여 최대 30회다. 재실행 후
상태 조회는 최대 두 번이며, 장시간 대기나 자기 자신 즉시 재실행을 하지 않는다.
네트워크/5xx/429의 읽기 재시도는 전체 점검당 한 번만, Retry-After를 지켜 수행한다.
401/403·미지원 경로는 즉시 중단한다. 예산 부족은 검증 생략의 이유가 아니다.

기동 요청 전에는 예약의 STATE에 run/job/예정 attempt/요청 시각을 미확인으로
기록한다. STATE만 갱신할 수 있으며 자동화의 일정·활성 상태·다른 지침은 바꾸지
않는다. 다음 점검은 이 요청의 결과부터 대조한다. tool 응답이 모호하거나 기동
보고서가 `request_unknown`이면 다시 보내지 않는다. 기존 요청을 확인할 run/attempt
또는 대상 watchdog 실행을 찾기 전까지 미확인을 유지하고 변화만 보고한다.
미확인 요청을 임의 TTL 만료로 실패/미발송으로 바꾸지 않는다.

개별 배치의 실패, 조사 자체의 실패, 정상 보호 조건에 따른 보류를 구분한다.
`retry_budget`은 상한 때문에 요청하지 않은 결과이며 게시 정상이라는 뜻이 아니다.
`inspection_failed`와 `request_unknown`은 기동 작업에서도 비정상 종료로 남긴다.

## 지속 가능한 seed와 한계

기동 workflow의 main 변경 push 및 기존 일일 콘텐츠 workflow 완료는 audit-only
seed를 만든다. 최초 자동 실행에는 POST가 불가능하다. 기존 예약을 늘리지 않고
재실행 가능한 최근 job을 확보하는 경로다. GitHub 실행 자체가 장기간 생성되지
않거나 seed를 확인할 수 없으면 이를 정상으로 가장하지 않는다. GitHub의 재실행
가능 기간은 최초 실행 이후 30일이므로 만료된 run 재실행을 복구 수단으로 삼지 않는다.

## 검증과 운영 보고

구현 검증은 최소한 오래된 완료 attempt, 실제 활성 작업, 같은 건수의 attempt 변경,
두 번째 검사에서 게시 성공, 슬롯·main 변경, 중지, 상한, 변조된 ZIP, 미확인 POST,
audit-only seed의 쓰기 금지를 포함한다. 원래 복구 제어기의 모든 회귀 검사도 유지한다.
운영 보고에는 배포 SHA와 실제 run/attempt/artifact, 수집·게시·readback 시각을 남긴다.
현재 회차의 실패·미확인과 과거 관측 공백을 보존하고, 관측하지 않은 순위를 만들지 않는다.
